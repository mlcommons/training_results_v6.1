# GPT-OSS 20B — single-node plan (MI355X, 1x8)

**Status: scoped, not yet started.** No code here yet; this document is the plan.

## Why this benchmark is the cheapest one to add

Everything the other three benchmarks made us build by hand already exists upstream for `gpt_oss_20b`:

| factor | status |
|---|---|
| Single-node support | **Reference ships `config_MI355X_1x8x1.sh`** — 1 node x 8 GPUs |
| Hardware match | **RCPs were generated by AMD on `1xMI355X`** — our exact accelerator |
| Dataset | **Already staged.** Same C4 files as `llama31_8b` |
| Framework | **Primus** — the stack we already debug daily |
| 8-GPU comparisons | **Published** (B300 83.62 min, GB300 75.26 min) |
| In 6.1 | Yes (`benchmark_meta.py` lists `gpt_oss_20b` under `'6.1'`) |

Contrast with `flux1`, where we had to invent a single-node config, move 2.3 TB, and where nothing below 32 GPUs was published.

MLCommons' own v6.0 announcement states the benchmark lets organisations evaluate MoE routing "on hardware configurations as small as a single 8-GPU node".

## The dataset is already on both nodes

The reference downloads `llama-3-1-8b-preprocessed-c4-dataset.uri` (~80 GB) and expects:

```
c4-train.en_6_text_document.{bin,idx}
c4-validation-91205-samples.en_text_document.{bin,idx}
```

Those exact filenames are already at `/lvol0/mlperf/llama31_8b/data` on lodin1 and lodin2, staged for `llama31_8b`. **Verify checksums before assuming they are identical**, but the naming is upstream-generated, so a match is expected.

Note this cuts both ways: if the files are shared, do **not** let a `gpt_oss_20b` staging script delete or rewrite them, or it will break `llama31_8b`.

## Convergence budget

Recomputed with the official `rcp_checker.py` statistics (olympic mean rejecting 1 per side; `min_epochs` from the binary-search t-test at alpha=0.05, `submission_runs=10`):

| GBS | RCP mean | min_epochs | headroom | lr | warmup | grad-accum | reference distribution |
|---|---|---|---|---|---|---|---|
| **16** | **194,560** | 188,719 | 3.09% | 4e-4 | 2,048 | 1 | 6x184320 11x196608 3x208896 |
| 32 | 234,837 | 229,259 | 2.43% | 8e-4 | 4,096 | 2 | 3x221184 12x233472 5x245760 |
| 64 | 301,056 | 290,308 | 3.70% | 1e-3 | 12,288 | 4 | 4x282624 7x294912 5x307200 2x319488 2x331776 |

**Start at GBS 16**: smallest sample budget (194,560, i.e. 17% cheaper than GBS 32) and grad-accum 1, which was the single best throughput lever on `llama31_8b` (+3.5%).

Caveat: the reference README documents GBS **16** with micro-batch 2 but quotes `Learning Rate 8e-4`, which is the **GBS 32** RCP value. The RCP hyperparameters, not the README table, are what the checker compares against. Resolve this before the first scored run.

## Memory

21B total / ~3.6B activated, seq 8192, expert-parallel 8. BF16 weights + fp32 master + AdamW m/v + grads is roughly 336 GB of state, about **42 GB/GPU** fully sharded across 8, against **288 GB** available. Comfortable, with room to trade sharding for speed.

## Plan

**Phase 0 — acquire the container (the one real unknown).**
AMD did *not* submit `gpt_oss_20b` in v6.0 (they submitted llama2, llama31, flux1), so there is probably **no `rocm/amd-mlperf:gpt_oss_20b_*` image**. Expect to either use a `rocm/primus` image or build from `mlcommons/training/small_llm_moe_pretraining/primus`. Resolve this first — it gates everything and is the only step with real risk.

**Phase 1 — verify data.** Checksum the C4 files against the reference manifest. No download expected.

**Phase 2 — smoke run.** `NEXP=1` from the reference `config_MI355X_1x8x1.sh`, unmodified. Confirm MLLog output and a sane samples/s before touching anything.

**Phase 3 — throughput.** Port the levers that worked on `llama31_8b`, which uses the same Primus/Megatron stack: `MLPERF_NUMA_BIND=1` (+1.8%), `CUDA_DEVICE_MAX_CONNECTIONS=8` (+1.5%), and avoid `GPU_MAX_HW_QUEUES=4` (-4.8%). MoE adds expert-parallel all-to-all, so communication tuning may matter more here than it did for dense llama31.

**Phase 4 — convergence placement.** Apply the llama2 lesson: check the eval-cadence quantisation (every 12,288 samples) against the RCP mean *before* optimising, since that quantisation decides whether early convergence is worth anything.

**Phase 5 — 10 scored runs.** ~10 x (single-run time), split across lodin1/lodin2 as independent workers.

## Expected cost

No published MI355X 8-GPU figure exists. Scaling from B300 at 8 GPUs (83.62 min) and assuming MI355X lands somewhat behind Blackwell Ultra on an MoE workload, budget **~100-130 min/run**, so **~20 h for a 10-run set** split across two nodes. That is comparable to `llama31_8b` and far cheaper than `flux1`.
